## Background and goals / 背景与目标

- 本期聚焦打怪升级相关的玩法数值：怪物基础经验、金币与物品掉落、爆率、刷怪，以及用户此前要求一并列出的相邻基础数据。服务器端口、线程数、并发数量、构建和部署参数不在本期讨论范围。
- 玩法值分散在 C++ 编译期记录、Lua 数据表/脚本及服务端已有内存字段。先盘点本期范围内所有字段及真实消费者，由用户决定哪些修改、哪些迁移以及如何迁移；不能代替用户筛选。
- 目标是把选定的既有玩法值从源码/脚本中的硬编码数据抽到配置系统，由游戏在启动或地图/脚本加载时读取。GUI 负责读取、编辑、校验和保存配置，游戏使用配置不依赖 GUI 常驻。
- 运行时加载不等于热更新。前期允许保存后下次启动/地图加载生效；不增加新的玩法参数，不改经验分配、掉落抽样、金币波动和补怪等计算逻辑。
- 用户提供就绪模板 `D:/SourceCodes/mywork/best-practices/templates/python-fastapi-webview`，作为 Python + FastAPI + pywebview + Vue 3/Vite 工作台的现成技术参考。规划时仅作技术参考；用户随后复制模板并授权全部实施，当前状态见总计划。

## Non-goals / 非目标

- 不讨论或迁移服务器/客户端端口、地址、线程池、并发容量、构建编译器、工具链、开发 profile 等基础设施配置。历史全量配置资料保留参考，不转化为本期任务。
- 初始规划阶段交付事实清单与计划；用户随后明确授权T01-T07实施与最终构建验证。在线热更新仍不在范围内。
- 不新增经验倍率、刷怪倍率等玩法能力，不接通现有未使用字段，不重写算法或调整业务流程。
- 不访问运行服、角色、用户数据库、凭据或私人部署配置；不练级、不安装到运行服、不启动或停止游戏进程；本地隔离构建/安装检查按后续授权执行。
- 不把“GUI 生成一串现有命令行”或“GUI 定点修改 C++ 后重新编译”当作已完成选定玩法值的运行时加载。

## Scenarios / 场景

- 用户查看经验、金币、掉落、刷怪的字段、当前值/单位、来源、消费者、约束及实际生效时机，逐项决定是否纳入管理。
- 用户同时看到相邻候选，如怪物战斗属性、药水/装备基础属性、物品价格、商店数据、固定奖励与地图放置；列出候选不等于批准迁移。
- 后续在 GUI 保存已迁移的玩法值，之后启动游戏或加载地图时，游戏自己读取同一份配置；未实现热更新时只显示“已保存，待加载”。
- 同一批配置迁移前后使用相同输入，应保持现有算法及数据语义：怪物/物品 ID 不重排、掉落分组与顺序不变、经验取整和金币波动不变、刷怪周期及密度计算不变。

## Risks / assumptions / 风险 / 假设

- `MonsterRecord` 与 `DBCOM_*` 目前用于编译期 ID 和 switch/case。外置经验不意味着将整套身份记录运行时化，必须另核各字段消费者。
- 掉落结果受分组内顺序、重复次数、既有倍率及随机波动影响；爆率不能一概简化为独立百分比。
- 刷怪 Lua 会向数据表写入 uidList、lastUpdateTime、gridCount，持久配置必须与这些运行状态隔离。
- 模板的 Dynaconf/Pydantic 只提供 Python 读取与校验；C++ 需自己的原生加载入口。保存文件不表示运行中的缓存已经更新。
- 旧 CSV/外部生成器和源码数据可能具有不同权威关系；迁移后只能有一个可维护数据源，不能双写或悄悄回退旧值。
