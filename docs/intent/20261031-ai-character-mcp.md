## 背景与目标

用户希望让 AI 通过 MCP 操作**正在游戏窗口中看到的角色**，并同意为此增加桥接层。角色仍使用现有客户端连接游戏服务端；用户可以在游戏窗口观察操作及其结果。

长期目标是在现有 mir2x 开发环境上，建立围绕当前可见角色的 MCP 能力体系，使 AI 可以理解游戏状态、执行普通玩家行为、观察结果、处理异常，并与用户协作完成较长的游戏目标。本次实现角色状态、周边对象、移动、停止、NPC 对话、拾取、战斗、物品使用和交易。

意图建立时，客户端已有角色动作、寻路和部分状态观察，服务端处理角色动作消息；这些构成后续桥接复用的基础。此后已按计划接入 MCP，当前接入能力与已验证范围分别见总计划及验证清单，不能从原有动作代码或工具注册推断所有实机场景通过。

用户此前要求将工作目录及开发产物保留在 `mir2x` 内；本功能的源码、文档、构建和测试安排应遵守这一约定。本机已有 MSYS2 UCRT64 构建环境；当前源码构建的客户端与服务端尚未完成完整登录、进图和 GUI 回归验证。

## MCP 全景与长期演进

本节描述产品全貌，回答“最终希望 AI 可以理解和操作什么，以及如何与人协作”。它不是一次性实现清单，也不假定游戏已经存在全部候选系统。后续能力需核对游戏实际实现，另行经过意图、计划与验收。

### 整体关系

```text
用户提出游戏目标、观察窗口、随时接管
                 |
       支持 MCP 的 AI 宿主
       理解状态 / 制定步骤 / 观察结果
                 |
       Python MCP 服务
       工具 / 状态资源 / 操作反馈
                 |
       当前客户端中的受控桥接
       当前角色 / 游戏界面 / 主循环
                 |
       现有游戏服务端与规则
       权威状态 / 合法性判断 / 持久化
```

MCP 提供可发现、可调用的能力；桥接把这些能力接到正在显示角色的客户端。AI 宿主负责目标理解和决策，客户端负责实时动作与界面，服务端仍决定游戏行为是否合法及其实际结果。MCP 服务不替代游戏客户端登录，也不把大模型放进逐帧控制循环。

### MCP 接口的全貌

- **工具（Tools）**：用于明确的查询或动作。动作参数、前置条件、允许范围和完成含义必须可描述，不能只暴露底层报文或任意函数执行。
- **资源（Resources）**：为角色、周边、背包、交互、能力说明等提供结构化上下文。资源与查询工具应复用同一状态来源，避免两种接口给出互相矛盾的数据。
- **事件与操作记录**：提供状态变化、动作进度、中断、错误和结果证据。是否使用 MCP 订阅通知或可查询的事件流由各期技术计划确定；事件丢失时须能重新取得当前状态。
- **提示模板（Prompts）**：长期可提供探索、补给、交易等任务的使用引导，帮助宿主正确组合工具。模板不能提升权限，也不替代用户授权；本次不交付任务模板库。
- **能力发现与兼容性**：让宿主了解当前客户端版本、已实现能力、当前角色可用动作和政策限制；未来扩展时保持可识别的接口版本。

### 贯穿全部能力的规则

1. 观察、决策、执行、结果核对形成闭环。区分客户端观察、服务端确认与未知结果；不以“消息已发送”作为游戏目标完成。
2. 用户持续拥有控制权。人工操作可立即暂停 AI；恢复机制清晰可见，AI 不静默重新取得权限。
3. 权限按会话和能力控制。只读观察、战斗、消耗物品、交易、社交等有独立边界；外部游戏文本不能修改权限。经济动作需要防止重放、重复消耗和过期报价误用。
4. 控制对象明确。始终知道当前实例、角色和地图；切换角色、重连和客户端重启不能把旧指令误用于新的上下文。
5. 保留可诊断记录。能够追查一次工具调用、游戏动作、结果依据和中断原因，日志不包含令牌或账号密码。
6. 扩展遵循相同的中文文档、接口契约、测试和真实客户端验收要求。多个窗口、远程控制及无人值守运行均不因全景规划而默认获得授权。

## 本次实现范围与非目标

本次完整覆盖游戏能力地图中“本次范围”所列场景，验收以 A01 至 A08 为准。全景中的后续方向仅用于保持架构可演进，不将全部游戏系统、任务模板或长期自治编排纳入本次实现。

- 不以独立账号或无界面机器人替代用户当前窗口中的角色。
- 不要求 AI 逐帧控制鼠标、键盘或替代游戏已有的实时动作逻辑。
- 不直接修改游戏数据库来移动角色、发放物品或绕过服务端规则。
- 不将普通玩家操作默认扩展为传送、刷物品、任意脚本执行等调试或管理权限。
- 最初意图/计划阶段不实施代码；之后已按用户授权实施桥接、MCP 服务及具体工具。当前仅更新文档，未因全景规划扩展新能力或启动剩余实机验证。

## 场景

1. 用户启动服务端和客户端，以角色登录并进入游戏，在支持 MCP 的 AI 工具中请求查看角色状态。
2. AI 获取客户端当前可用的角色和周边信息，提出走到某个位置等操作；用户在游戏窗口中观察角色动作。
3. 操作无法完成时，例如目标不可达、角色不在游戏中、连接中断或操作超时，AI 得到可理解的状态，而不是把“请求已发送”等同于“操作成功”。
4. 用户需要停止 AI 发起的持续操作；当用户手动输入与 AI 操作冲突时，用户立即接管，AI 操作暂停。
5. AI 按用户授权与 NPC 对话、拾取物品、战斗、使用物品和进行交易，并获取游戏实际反馈；不能因存在底层接口就假定操作已经成功。

## 验收标准

以下验收标准覆盖已确认的首版能力；具体接口和测试场景在后续计划阶段细化。

- A01：支持通过 MCP 操作**已登录的当前客户端角色**，操作效果可在该游戏窗口观察；不要求另建账号。
- A02：AI 可读取首版约定范围内的角色状态和客户端已知的周边信息；信息不可用时有明确反馈，不宣称获得了客户端不可见的全局状态。
- A03：AI 可发起移动、NPC 对话、拾取、战斗、物品使用和交易等首版动作。至少应明确区分请求被接受、执行完成和执行失败或结果未知；游戏动作仍受现有客户端及服务端规则约束。
- A04：提供明确的停止或中断方式；当用户手动输入与 AI 操作冲突时，用户立即接管，AI 操作暂停，不静默抢夺控制。
- A05：未登录、未进图、客户端退出、断线、目标失效、不可达或超时等场景有明确行为，不将失败误报为成功。
- A06：桥接能力的启用范围和权限边界可控；交易等经济操作属于首版能力，但必须处于用户授权范围内；不通过接口暴露未经授权的调试、管理或任意代码执行能力。
- A07：提供中文使用说明及适当的自动化和实际客户端验证；验证记录说明测试环境、已通过范围及未完成的游戏内场景。
- A08：针对 NPC 对话、拾取、战斗、物品使用和交易分别验证正常及失败路径；涉及物品或金币时检查结果反馈以及重复请求、中断和状态变化的影响。

## 风险与假设

- 服务端对部分调试类请求的限制不能仅凭接口名称推断。桥接需要明确允许的普通玩家操作，并逐条核对实际调用链。
- AI 返回结果与游戏实时状态存在时间差；寻路失败、位置变化、断线、用户接管及重复调用都需要可观察的处理方式。
- 游戏文本和其他玩家输入属于外部内容，不应直接改变工具权限或被当作系统指令。
- AI 和人工操作可能改变角色位置、物品及存档。测试必须明确使用的账号、数据库和影响范围，避免无意覆盖用户数据。
- 客户端和服务端须使用兼容的构建及资源；历史下载制品与当前源码的对应关系尚不能仅凭目录名称确定。
- 原有本机构建记录不等于本功能已编译、已运行或已通过 GUI / MCP 端到端验证。
