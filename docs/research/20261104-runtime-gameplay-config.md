## 背景与目标

刷怪、经验、掉落等数值目前分散在服务端窗口、启动参数、Lua 脚本和公共静态记录中。部分字段虽然有配置入口，却没有接入实际结算。

当前目标是让维护者通过界面管理已经存在的配置，减少在多个脚本、窗口和源码文件之间查找、手工改值的工作。可视化编辑沿用现有数据来源和业务计算，不要求保存后立刻改变正在运行的游戏。

此前讨论的长期目标是服务端和客户端保持运行时调整玩法参数。文件加显式重载、进程间分发及必要的客户端同步仍有参考价值，详见后文“历史方案：运行时配置与同步”；本轮先评估配置管理本身。

## 配置清单与现有管理方式

以下结论来自源码检查，未核对当前运行服的实际配置或进行现场操作。状态标记的含义：

- **原有**：当前已有字段、启动参数、脚本数据或源码常量，不代表一定能运行时调整。
- **原有未接入**：字段或界面存在，但尚未用于对应业务计算。
- **建议新增**：讨论中建议的配置能力或名称，目前不是产品接口。
- 下表的 **热更新批次** 沿用此前的运行时方案建议，不表示本轮可视化范围或已实现功能。本轮的实施优先级另见“本轮评估：原有配置的可视化管理”。

## 当前源码机制

### 刷怪

[地图脚本](../../server/script/map/边境城市_01.lua) 使用 [addmonster.lua](../../server/script/map/addmonster.lua) 的 `monGener()` 创建生成协程。一个区域的配置示例：

```lua
{x = 450, y = 250, w = 50, h = 50, count = 30, time = 600}
```

生成器保存 `uidList` 和 `lastUpdateTime`。到检查周期后，清理死亡记录并尝试补足目标数量。当前目标数量还受可通行格数和密度约束：

```lua
math.max(1, math.min(math.floor(gridCount / 8), count))
```

因此不能仅把现有 `count` 乘以零就认为关闭了生成。运行时开关应在生成检查中明确处理。

以边境城市脚本为例，`main()` 每约五秒恢复一次生成协程；具体检查精度还受各地图脚本调度影响。地图创建时加载脚本，修改磁盘文件不会自动更新已经运行的协程。

### 经验与掉落

- [Monster::dispatchOffenderExp](../../server/src/monster.cpp) 根据近期攻击者伤害占比分配怪物记录中的 `.exp`。
- [Player::on_AM_EXP](../../server/src/playerop.cpp) 处理经验消息及可见队友分配，随后调用 `gainExp()`。
- [Player::gainExp](../../server/src/player.cpp) 增加累计经验、更新数据库并发送 `SM_EXP`。
- 当前窗口的 `experienceRate` 只有定义、显示及赋值，未被上述经验发放路径读取，也不在当前 `SDPeerConfig` 的分发字段中。
- [getMonsterDropItemList](../../server/src/dropitemconfig.cpp) 已读取当前 `dropRate/goldRate`；[PeerConfig](../../server/src/peerconfig.hpp) 和 [AM_PEERCONFIG 处理](../../server/src/peercoreop.cpp) 可作为配置分发的现有基础。

击杀倍率应在击杀经验计算中应用一次，之后按正常逻辑分配给攻击者和队友。任务经验保持独立，避免在所有来源共用的 `gainExp()` 中统一乘倍率而发生重复放大。

## 本轮评估：原有配置的可视化管理

### 可行性与总体判断

可行，而且比同时建设统一配置、运行时重载和客户端同步更容易分阶段交付。核心工作是把现有文件和字段转换为可编辑表单，再可靠地写回原来的来源。游戏业务可以继续使用现有加载方式。

不过，“原有配置”不全是可直接读写的配置文件：有的是窗口内存值，有的是 Lua 数据表，还有的是编译进程序的 C++ 记录或计算函数。因此应提供统一的管理入口，按来源分别处理保存，不能把所有项目都当成修改一个 JSON 文件即可生效。

| 原有配置类别 | 适合的界面 | 保存及使用方式 | 评估与建议顺序 |
| --- | --- | --- | --- |
| 启动设置：网络地址、玩家/节点端口、程序路径、启动参数 | 分组表单、目录/文件选择、开关 | 当前 `main` 使用原生启动参数；若恢复 `develop` 历史 launcher，可复用其 TOML。持久化入口需随具体实现确定 | 工作量较小，适合第一批 |
| 服务端窗口：`dropRate`、`goldRate`、最大人数、地图/脚本路径 | 沿用已有 ConfigureWindow，补充分组和说明 | 现有窗口主要更新内存；新增跨重启保存需要单独实现持久化和启动读取 | 基础界面已存在，优先复用；持久化不能当成已有能力 |
| 刷怪区域：怪物、`x/y/w/h`、`count`、`time` | 地图列表 → 怪物 → 区域表格；可选地图矩形预览 | 写回支持的地图 Lua 数据段；下次重新创建相应脚本环境时读取 | 使用价值高、工作量中等，建议第一批重点 |
| 怪物基础记录：经验、血量、攻击、防御等 | 搜索列表与详情表单 | 写回 `common/src/monsterrecord.inc`；重新编译受影响程序并部署 | 工作量中等，建议第二批开放编辑 |
| 单怪物掉落表 | 按怪物筛选的表格、物品选择、分组显示 | 写回 `server/src/dropitemconfig.inc`；重新编译并部署服务端 | 工作量中等，建议第二批 |
| 物品定义、等级曲线、密度常量 | 物品记录先查询；曲线预览；高级源码入口 | `.inc` 需要编译，`SYS_SUMEXP` 等还涉及公式代码；公共记录须保持客户端/服务端一致 | 先只读，按明确需求逐步开放 |
| 任务经验和其他任务奖励 | 任务列表、源码定位；已适配模板才提供表单 | 修改对应 Lua，按现有脚本生命周期加载 | 逻辑形态不统一，后续按任务模板接入 |

`experienceRate` 虽然已有输入框，但当前没有接入经验发放。本轮应标注“字段存在，结算未使用”，可先只读展示；不能通过补一个界面就宣称能够调整击杀经验。原有的怪物 `.exp` 才是本轮可以管理的真实基础经验数据。

### 界面按玩法分组，字段标明来源

建议界面使用以下分组，延续前面的原有/建议区分：

1. **运行设置**：网络、端口、程序与资源路径、原有启动开关。
2. **刷怪配置**：按地图和怪物筛选，编辑区域坐标、大小、目标数量和补怪周期。
3. **怪物属性与经验**：基础经验、血量、攻防、移动/攻击间隔等原有记录；已有未接入字段单独标记。
4. **掉落与金币**：原有全局倍率、怪物掉落明细；显示概率倒数、尝试次数和分组的实际含义。
5. **物品与等级资料**：先提供查询、引用关系和等级曲线预览。
6. **任务奖励**：先提供查找和源码定位，再考虑已知模板的结构化编辑。

每个可编辑项展示来源文件/字段、单位、磁盘保存值，以及“下次启动读取”“需重新加载脚本环境”“需重新编译部署”之类的使用条件。未读取运行进程时，界面只称“文件值”或“待保存值”，不把它显示为当前游戏实际值。

数据库文件目前固定为服务端工作目录下的 `mir2x.db3`，界面可展示解析后的路径；提供独立数据库路径选择器需要新增产品参数，不属于本轮已有配置编辑。

`kill_exp_multiplier`、`spawn_count_multiplier` 等建议项留在研究清单，不放进可编辑的原有配置表单。新的可视化工具、持久化和文件适配器本身属于待开发的管理能力，与新增玩法参数分开标记。

### 简单实现方式

推荐先做本地配置编辑器：选择源码目录或发行目录后，按实际存在的来源启用对应页面。只有发行文件的目录可以管理启动设置和已部署脚本；没有源码时不提供 `.inc` 编辑和编译入口。界面技术在后续 Plan 确定，当前不需要引入远程管理服务或配置中心。

服务端窗口已有 FLTK 表单，应优先复用其字段含义和现有入口。若只改善几个全局字段，扩展 ConfigureWindow 成本较低；若主要管理地图刷怪、怪物和掉落表，则独立编辑器更合适，因为这些工作不依赖服务器正在运行。两者应共享清楚的数据来源，不各自维护一份无法对应的值。

建议保持简单的操作流程：

1. 读取原文件，将支持的字段显示为表单或表格。
2. 编辑时校验类型、单位和引用；保存前预览本次差异。
3. 检查文件是否已被其他编辑器修改；冲突时重新加载，避免覆盖。
4. 备份原文件，再通过临时文件替换保存；失败时保留原文件。
5. 显示文件已保存及后续加载/编译要求，编译和启动操作另行明确执行。

本轮不必先新增 `config/gameplay.json`，否则还要为业务增加加载入口并处理它与原文件的优先关系。对于窗口内存配置，如果确有跨重启保存需求，再给现有字段增加一套明确的保存和读取流程；当前 launcher TOML 没有 `dropRate/goldRate` 等字段，不能直接把它们写进去并期待生效。

### 各来源的关键边界

**刷怪 Lua。** 已有地图脚本将 `monGener` 数据表与守卫创建、协程调度等逻辑放在同一个文件。首期只支持已识别的字面量数据表，保留其余脚本及注释；遇到函数计算、动态生成或不支持的写法时转为只读/源码编辑。不能依靠宽泛正则重写整份 Lua，也不应为了读取配置直接执行地图脚本。也可在后续实现中显式迁移为独立数据文件，但这会修改现有加载方式，须另列实施范围。

刷怪表单应说明 `time` 单位为秒、`count` 为区域目标数量，实际数量还受可通行格数及密度限制。现有逻辑将区域上限至少取为 `1`，所以 `count=0` 不能作为关闭刷怪的界面约定；全局关闭使用已有启动参数。地图预览可先做矩形显示，复杂底图和拖拽编辑后置。

**C++ 静态记录。** `.inc` 是 C++ 初始化数据，当前没有可直接复用的通用表单读写层。首期适配明确字段，遇到未支持表达式时保留原文或拒绝写入。`monsterrecord.inc/itemrecord.inc` 的记录顺序参与 ID 映射，界面排序只改变显示顺序；不能在保存时重排、删除或重新编号已有记录。记录属性编辑与增删实体分开评估。

**掉落表。** `probRecip` 表示概率倒数，`repeat` 表示尝试次数，非零 `group` 约束同组至多掉一项。表格可以辅助显示基础概率，但不能把有分组、多次尝试和全局倍率的实际结果简单展示成一个无条件百分比。源码注明掉落表由 `dropgen.py` 生成，实施前需确认后续维护以生成器输入还是 `.inc` 为权威，避免下次生成覆盖界面修改。

**原有倍率。** 当前窗口允许非负倍率，但掉落实现涉及概率倒数除法，金币数量又有至少 `1` 的限制。表单不能自行把 `0` 解释为关闭掉落/金币；如要开放零值，需要先明确并验证现有计算语义。仅做可视化时，先沿用经过验证的正值范围，不扩展玩法承诺。

**任务和等级。** 任务奖励可能位于条件分支或通过变量计算，`SYS_SUMEXP` 是函数而非一列配置数据。通用可视化改写成本较高，先展示现有内容和定位入口更合适；对固定模板的编辑另行适配。

### 建议分期与检查

| 阶段 | 交付重点 | 本阶段的边界 |
| --- | --- | --- |
| 第一批 | 原有配置目录、启动设置表单、已知地图刷怪表格，补充现有服务端窗口字段说明 | 使用原数据来源；刷怪保存不重写其他脚本；未接入经验倍率明确标注 |
| 第二批 | 怪物基础属性、单怪物掉落表的结构化编辑 | 明确生成器权威；保存后需要编译；公共记录保持 ID 和客户端/服务端一致 |
| 后续 | 地图拖拽、物品编辑、任务模板、等级公式辅助编辑、窗口配置持久化 | 按真实使用频率逐项扩展，不要求一次覆盖全部来源 |

本轮评估认为整体复杂度中等，主要成本在 Lua/C++ 数据的可靠往返保存，而不是界面控件。若只做已有窗口字段整理和 launcher TOML 表单，范围较小；纳入地图、怪物和掉落编辑后，需要逐类适配，不能按一个通用键值表估算。

后续实施检查应围绕：读取字段与原文件一致；未修改保存不产生无关差异；只改变指定字段；注释和脚本逻辑保留；不支持格式拒绝写入；文件冲突不覆盖；无效引用/数值有字段反馈；备份可恢复；保存提示与真实加载、编译要求一致。脚本和静态记录在隔离环境进行语法/构建检查即可，不以在线调整当前运行服为本轮验收条件。

## 历史方案：运行时配置与同步

以下保留此前的热更新研究建议，供后续再评估。本节的“首期”指原运行时方案，不代表本轮可视化管理已经决定新增这些能力。

### 配置文件与重载入口

建议新增运行目录配置文件，例如 `config/gameplay.json`。路径及命令名为研究建议，尚未确定为产品接口：

```json
{
  "kill_exp_multiplier": 1.0,
  "drop_multiplier": 1.0,
  "gold_multiplier": 1.0,
  "spawn_enabled": true,
  "spawn_count_multiplier": 1.0,
  "spawn_interval_multiplier": 1.0
}
```

修改文件后，通过运行管理 CLI 或管理 MCP 调用一次重载。入口具有服务端管理权限，与普通角色动作权限分开。首期不依赖文件监听，也不要求操作服务器窗口。

重载做基本的类型、有限数值和范围检查；整份解析成功后替换内存配置，失败保留原配置并返回具体错误。采用一份小型类型化结构，通过现有进程消息分发方式供业务读取。已有窗口如继续保留，使用同一配置入口，避免窗口和文件各维护一份独立值。

提供查询当前实际值和最近加载结果的能力，并记录修改前后值及加载时间。恢复旧值可修改文件后再次重载。首期不建设复杂的配置中心、审批流或跨进程事务系统。

### 服务端何时使用新值

| 参数变化 | 建议生效时点与行为 |
| --- | --- |
| 击杀经验倍率 | 下一次击杀经验结算使用新值，不改写已发经验 |
| 掉落、金币倍率 | 下一次对应掉落计算使用新值，不重新计算已有掉落或余额 |
| 关闭刷怪 | 下次生成检查停止新增，已有怪物继续存在 |
| 增加目标数量 | 后续检查尝试补充，避免一次大量生成造成卡顿 |
| 降低目标数量 | 停止补充至数量自然下降，不直接删除现存怪物 |
| 修改补怪周期 | 保留上次检查时间，以新周期进行后续判断 |

生成器每轮读取当前配置，保留原协程、`uidList` 和 `lastUpdateTime`。关闭后重新开启也不丢失存活怪物记录，避免重复补出一批。每次结算或生成检查开始时读取一份配置即可。

### 客户端如何动态响应

大多数服务端参数可以沿用现有游戏结果消息，客户端无需自行重新计算服务端规则：

| 参数变化 | 客户端处理 |
| --- | --- |
| 经验倍率 | 接收实际 `SM_EXP`；如需倍率提示，再同步展示字段 |
| 刷怪数量、周期 | 接收正常怪物出现、行动和消失消息 |
| 掉落、金币倍率 | 接收真实地面物品、背包和金币变化 |
| 需要展示的规则 | 通过现有游戏连接接收一份小型完整配置，更新本地缓存及界面 |

必要的配置同步采用服务端主动推送；登录时再发一次当前完整值，覆盖后来上线的客户端。需要缓存的配置放在能跨场景加载存续的位置，避免仅在 RUN 界面存在时才能接收。

首期不要求逐客户端确认或复杂增量同步。服务端始终决定实际经验、掉落和生成结果。首次增加配置能力及消息需要发布相应代码，之后只调整已登记参数时，服务端和客户端均可继续运行。

### 运行时方案的落地顺序与后续检查

1. 建立小型配置结构、文件加载、查询和重载入口，接通经验、掉落、金币三个倍率。
2. 让现有 Lua 生成器读取刷怪开关、数量和周期倍率，保留已有生成状态。
3. 按实际界面需要增加公开配置同步；后续再考虑任务经验倍率、密度和地图覆盖。

后续实施至少检查：合法配置运行中生效；错误文件保留旧值；已连接客户端无需重登即可看到实际结果；刷怪关闭不新增、重新开启不重复计数；倍率只在对应结算应用一次；服务端重启后能够加载保存的配置。

首期复杂度中等，主要修改点跨越配置入口、经验和掉落计算、Lua 生成器及必要的客户端消息。当前仅记录建议顺序，不建立 task、DAG 或会话分配；这些工作在具体实施计划中确定。

## 已确认决策与待确定细节

已确认的用户要求：

- 希望服务端和客户端运行期间能响应服务端玩法配置变化。
- 简单、高效优先，不追求百分之百严谨。
- 将当前讨论整理到 `docs/research`。
- 本轮先评估原有配置的可视化管理，暂不考虑 MCP 接入和即时生效。

本轮研究建议：

- 以本地编辑器管理原有来源，按启动设置、刷怪、怪物、掉落等分组。
- 第一批聚焦启动设置与已知刷怪数据；静态记录分批接入，任务和公式先只读。
- 保存、编译部署和运行时加载分别说明；原有未接入字段不显示为可用玩法控制。

此前运行时研究建议，留待后续：

- 采用文件加显式重载，复用现有通信路径。
- 首期聚焦六项全服参数；其他项目保留清单，按实际需求接入。
- 已有游戏结果消息可以表达变化的，客户端继续消费实际结果。

可视化实施计划仍需确定：

- 优先扩展现有 FLTK 窗口，还是建立覆盖地图、怪物和掉落的独立本地编辑器。
- 第一批支持的具体地图 Lua 结构、字段及遇到动态脚本时的只读边界。
- 静态记录的解析/写回方式，以及掉落生成器输入与生成文件的权威归属。
- 窗口配置是否要求跨重启保存；若要求，确定保存位置和启动读取方式。
- 地图预览、编译辅助操作是否进入首批。

后续运行时方案仍需确定：

- 配置文件的最终路径、加载默认值及重载命令名称。
- 各倍率的合法范围、取整方式，以及零值的准确含义；补怪周期需有正的下限。
- 配置文件与已有窗口的统一管理方式。
- 首期界面需要展示哪些字段，以及是否需要新增配置同步消息。

这些细节尚未构成已接受的完整实施计划。本次文档更新核对了 `serverconfigurewindow.fl`、`runtime_config.py`、launcher 默认 TOML、地图 Lua/生成器、掉落计算及静态记录等源码依据，检查文档结构与相对链接；未实现可视化界面，未运行游戏、构建程序或变更运行参数。
